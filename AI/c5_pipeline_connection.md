# C-5 전처리와 프로젝트 연결 설명

아래는 `my-dd` 관제센터에서 `message`가 분석 결과로 변환되는 흐름이다.

1. Dashboard에서 사건 `message` 입력  
2. 프론트엔드가 Flask `POST /ingest` 호출  
3. 서버가 사건을 Kafka로 발행하거나(가능 시), fallback으로 즉시 처리  
4. Consumer 또는 서버 내부 분석 함수가 사건 문장을 받음  
5. 전처리 수행  
   - 토큰화(tokenization)  
   - 정수 인코딩(integer encoding)  
   - 원-핫 인코딩(학습 이해용) 또는 임베딩(실서비스용)  
6. 모델 추론 또는 규칙 기반 추론 수행  
7. `event_type`, `severity`, `summary` 같은 결과 생성  
8. 결과를 저장소(DB)에 기록  
9. Dashboard가 `/events`, `/events/<event_id>`로 결과를 조회해 화면에 표시

---

## 전처리는 어디서 수행하는가?

전처리는 한 위치에 고정되는 것이 아니다.

- Flask 라우트에서 선처리 가능  
  - 입력 검증, 공백 제거, 기본 정규화
- AI 분석 함수(`model_inference`)에서 전처리 가능  
  - 모델 입력 포맷에 맞춘 토큰화/인코딩
- Consumer에서 전처리 가능  
  - 비동기 파이프라인으로 대량 처리 시 유리

즉, 시스템 구조(동기/비동기), 트래픽, 운영 편의성에 따라 배치 위치가 달라질 수 있다.

---

## Kafka가 있을 때 전처리 위치를 어떻게 볼까?

- `ingest` 단계: 최소 검증만 수행하고 빠르게 큐에 적재
- `consumer` 단계: 무거운 전처리/추론 처리
- 장점: API 응답 지연 감소, 재처리/확장성 개선

반대로 Kafka가 없으면 Flask 내부 fallback 경로에서 전처리+추론을 즉시 수행할 수 있다.

---

## 원-핫 인코딩과 임베딩

- 원-핫 인코딩
  - 장점: 구조 이해가 쉽고 해석이 직관적
  - 단점: vocabulary가 커질수록 벡터가 길어지고 희소해짐
- 임베딩
  - 장점: 밀집 벡터로 메모리 효율적, 단어 의미 유사도 반영 가능
  - 실서비스에서는 보통 임베딩을 사용

---

## 기본 구조 대비 완성형으로 확장된 점

- 단순 이벤트 표시에서 끝나지 않고, 분석 파이프라인 위치를 명확히 설명 가능
- `message -> 숫자 벡터 -> 추론 결과 -> Dashboard 표시`의 전 단계를 연결해 설명 가능
- AI 모델 부재 시에도 rule/mock/fallback으로 서비스 흐름을 유지할 수 있음
